# 05 — Manual Send UI

## 1. Frontmatter
See YAML header above. Every field must be filled before validation.

## 2. Goal
Give the owner a **local web page** on this laptop to send the to-do list by hand — to chosen people, on WhatsApp and/or email, in `dry-run`, `self` or `live` mode — and to **see, in one place, whether each message really went**. It sits on top of modules 02 and 04 and calls them exactly as published (`--people`, `--resend`, `--trigger manual-ui`, `--reconcile`); it adds no sending logic of its own, so a manual send obeys the same idempotency, pacing, caps, timeouts and logging as the 10:00 run. Owner decisions of 2026-10-19: a local web page (not a desktop window); a person who already got today's list may be sent it again, but only after an explicit confirm; the UI sends from today's list and offers a **Rebuild list** button instead of rebuilding silently.

**Why a UI at all, given the automation.** The 10:00 run covers the normal day. The UI covers everything else: a late task someone must hear about now, a message that never arrived, a correction after fixing an address, a test before trusting a change. Doing that by hand today means remembering command-line options for two modules and reading two JSON logs.

> **Explore findings (2026-10-19, read-only).**
> - **Environment:** Python 3.14.7; **Flask 3.1.3** and Werkzeug 3.1.8 are installed (no `waitress`, none needed for one local user); ports 8765/5000/8080 are free.
> - **Host protection works:** with `TRUSTED_HOSTS = ["127.0.0.1","localhost"]` Flask 3.1 answered a forged `Host: evil.example` with **400**, and a cross-site POST arrives with `Origin` and `Sec-Fetch-Site: cross-site` that the server can reject. A page that can trigger real sends must be safe from other websites in the owner's browser (DNS rebinding, cross-site form posts), so R2 is not optional.
> - **The Desktop is a cloud folder.** `[Environment]::GetFolderPath('Desktop')` is `G:\My Drive\…\Desktop`, a Google-Drive-synced folder. A shortcut there would sync a path from this laptop to the cloud; R18 puts the shortcut in the Start Menu instead.
> - **History exists in two places.** The shared ledger's first row is **2026-10-19 13:01** (16 dry-run rows from module 03's real test); the 30 days before that — 39 runs, **44 real WhatsApp `sent`** — live only in module 02's `send_log.json`, which has no `delivery` field and a `trigger` on only 1 of 39 runs. A log page that read only the ledger would look empty for history, so R13 merges both.
> - **Who exists where:** WhatsApp contacts are 6 people (Rabbani, Rashikul, Mamun, Robiul, Alim, Kalam) with two days each; email contacts are 4 (Rabbani, Rashikul, Mamun, Robiul), all `Sat,Wed`. Alim and Kalam are WhatsApp-only. The days differ per channel (e.g. Rabbani: WhatsApp Sun/Wed, email Sat/Wed), so "due today" is computed per channel.
> - **The scheduler's lock is the WhatsApp safety.** Module 02 has no lock of its own; module 03's `outputs/03-scheduler/run.lock` (atomic create, `{pid, started}`, stale if the pid is dead or older than the timeout) is what keeps two WhatsApp sessions off the shared Chrome profile. A UI job that holds it when 10:00 arrives makes the scheduled run log `skipped_locked` — which is **not** retried — so the UI needs a guard around `SCHED_TIME` (R10). Module 04 has its own lock, and module 03's email step treats a locked module 04 as `email_failed`, which *is* retried, so an email-only UI job needs no such guard.
> - **Cost and time of a rebuild:** the real end-to-end dry-run of 2026-10-19 (modules 01 + 02 through Claude) took 73 s and $0.29; module 01 alone is expected to be about 1–2 minutes and a few tenths of a dollar. A WhatsApp send of one or two people took 43–49 s in the module 02 tests; an email send about 40 s (30 s of that is the bounce wait).

## 5. Scope
**In scope**
- A local web page: **Send** (choose people and channels, preview, mode, confirm, run, watch progress, see per-person outcomes) and **Log** (the delivery history with filters, colours and CSV export), plus a status strip and the **Rebuild list** and **Refresh email receipts** jobs.
- Server-side validation of every request independent of the browser; one job at a time; the scheduler's lock for WhatsApp jobs; a guard around the 10:00 run.
- A launcher (`start_ui.cmd`), a Start Menu shortcut, and single-instance handling.

**Out of scope**
- Anything remote: no LAN access, no login accounts, no HTTPS (loopback only), no cloud.
- Sending logic of any kind — the modules do that; and **changing** modules 01–04 (all called as published).
- Editing contacts, schedules, messages, `scheduler.env` or `.secrets/` from the page (including switching the scheduled email channel on or off — it only *shows* that state).
- Refreshing WhatsApp delivery receipts after the run: module 02 can only see a receipt while its worker is connected (module 02 §5), so the Log page says so instead of offering a button that cannot work.
- Cancelling a running job (every job is bounded by its module's own ceiling), scheduling a send for later, and any message editing.
- A mobile layout or multi-user use.

## 6. Requirements
| ID | Requirement (testable) |
|---|---|
| R1 | The server is `src/ui/app.py` (Flask). It binds **only** to a loopback address (`127.0.0.1`, port `UI_PORT`, default **8765**) and refuses to start with any other host (`0.0.0.0`, a LAN address, `::`). `TRUSTED_HOSTS` is `["127.0.0.1", "localhost"]`, so a request carrying another `Host` header (DNS rebinding) gets **400**. |
| R2 | **Access control.** At start the server makes a random token (≥32 bytes) and keeps it **in memory only**. The launcher opens `http://127.0.0.1:<port>/?t=<token>`; the first visit sets a cookie (`HttpOnly`, `SameSite=Strict`, session) and redirects to the clean URL. Every route except that first visit requires the cookie (otherwise **401**). Every `POST` additionally requires a same-origin request: `Origin` (when present) equals the page's own origin and `Sec-Fetch-Site` (when present) is `same-origin` or `none` — otherwise **403**. Nothing is ever sent, started or changed by a `GET`. |
| R3 | **One instance.** On start the server writes `outputs/05-manual-ui/ui.json` (`pid`, `port`, `started`, **no token**). A second start finds a live pid, does not start another server, and tells the owner the UI is already running (and where); a stale file (dead pid) is replaced. `start_ui.cmd --stop` ends the server and removes the file. A new token is made on every server start, so an old URL stops working. |
| R4 | **Send page — the table.** One row per person present in either contact file (excluding `No Name` and the owner's own group), with, per channel (WhatsApp, Email): the person's item count from today's list; whether the channel's `Send days` includes today; the **state today** from the module's own log (`not sent`, `sent HH:MM · delivered` / `server` / `pending`, `unconfirmed`, `failed`, `bounced`, `queued`, `dry-run done`, `no items`, `not on this channel`); and a checkbox. Pre-ticked: due today, has items, not already sent live today, and (email) a valid address. Everything else is unticked, never hidden. |
| R5 | **List freshness.** The page shows when `todo_by_name.json` was written. If it is from today: normal. If it is from an earlier day or missing: a prominent banner, **all send controls disabled**, and **Rebuild list** offered. (Modules 02 and 04 refuse a stale list anyway — R13/R22 of theirs — so this is the same rule, shown early.) |
| R6 | **Preview.** Each row can expand to show exactly what would go out: the WhatsApp text, and the email subject and body text, produced by calling module 02's `build_message` (and module 04's subject/signature settings) — so the preview *is* the message, never a re-implementation — with no log row, no ledger row, no Outlook, no WhatsApp. |
| R7 | **Modes and confirms.** The mode selector offers `dry-run` (the default, **reset on every page load, never remembered**), `self` (messages go to the owner's own test number / `me`), and `live`. The page colours itself by mode (live is unmistakable). `live` needs an explicit confirm step listing "WhatsApp: N people · Email: M people — these go to real people" and a ticked box. A person already sent live today on a channel needs a **separate** confirm line naming them and the time of the first send ("send again?"), and is then sent with `--resend`. |
| R8 | **Running a send.** A Send request runs the chosen channels **one after the other** (WhatsApp, then email); a failure of the first does not stop the second. Each is the module's own command line: `python …/send_whatsapp.py --people <A,B> [--resend] --trigger manual-ui` and `python …/send_email.py --people <A,B> [--resend] --trigger manual-ui`, with `WA_MODE` / `EMAIL_MODE` set to the chosen mode in the **child environment only**. `--resend` is passed only for people who were already sent live today on that channel and confirmed (R7). The UI never uses a module's internals to send. |
| R9 | **The scheduler's lock.** Any job that touches WhatsApp's browser session (a WhatsApp send) **or** runs Claude (Rebuild list) first takes `outputs/03-scheduler/run.lock` by **atomic create** with the same `{pid, started}` shape the wrapper uses, and releases it in a `finally`. If a live lock is held (a scheduled run, or another job) the job is refused with who/since, and those controls are disabled while it lasts. A lock whose pid is gone, or older than 30 minutes, is reclaimed. Email-only jobs take **no** scheduler lock (module 04's own lock covers them). |
| R10 | **The 10:00 guard.** A lock-taking job (R9) is refused if its start falls in `[SCHED_TIME − 6 min, SCHED_TIME + 3 min]` (`SCHED_TIME` read from `scheduler.env`, default 10:00), with the reason shown: a scheduled run that finds the lock held logs `skipped_locked` and is **not** retried, so holding it at 10:00 would silently skip the day. Email-only jobs are unaffected (a locked module 04 makes the scheduler's email step fail and retry, which is the safe direction). |
| R11 | **Rebuild list.** A `Rebuild list` job runs the headless Claude session for **module 01 only**: `claude -p --settings src/scheduler/scheduler.settings.json --permission-mode manual --permission-prompts none --output-format json`, the prompt from `src/ui/rebuild_prompt.txt` on stdin, working directory the repo root, exactly the flags and restrictions of module 03 (R5–R7 of its plan). It takes the scheduler lock (R9) and obeys the 10:00 guard (R10). |

## 7. Steps / Design
```
Browser  ──(127.0.0.1 only · token cookie · same-origin POST)──►  src/ui/app.py  (Flask, threaded)
                                                                     │  GET /            Send page: status strip, freshness banner, table, preview
                                                                     │  GET /log         Log page: filters, colours, CSV
                                                                     │  GET /api/state   today's table as JSON · GET /api/job  progress
                                                                     │  POST /api/send   validate (R17) → one job
                                                                     │  POST /api/rebuild · /api/reconcile
                                                                     ▼
                                              job thread:  [take scheduler lock if needed (R9, R10)]
                                                           WhatsApp step ─► python send_whatsapp.py --people … --trigger manual-ui   (WA_MODE=<mode>)
                                                           Email step    ─► python send_email.py    --people … --trigger manual-ui   (EMAIL_MODE=<mode>)
                                                           [release lock]  →  re-read module logs → per-person outcome
```
Files (all new; nothing in modules 01–04 is modified):
- `src/ui/app.py` — routes, validation, job runner, lock helper, log merge.
- `src/ui/templates/{base,send,log}.html`, `src/ui/static/{style.css,app.js}` — no external assets.
- `src/ui/rebuild_prompt.txt` — module 01 only, with the same "never ask, never write outside `outputs/`, no git, no secrets" rules as module 03's prompt.
- `src/ui/start_ui.cmd`, `src/ui/make_shortcut.ps1`.
- `.claude/skills/05-manual-ui/SKILL.md` (written at the SKILL phase).

**Server start.** `app.py` parses `--host/--port` (host validated loopback, R1), creates the token (R2), checks `ui.json` for a live instance (R3), writes it, registers cleanup, and serves with Flask's own server (`threaded=True`, no reloader, no debugger — the Werkzeug debugger would allow code execution from the browser and must never be on). The only third-party import is Flask (R20); there is no build step and no package installed at runtime. Job execution is serialised by one in-process job slot plus the file locks of R9, so two simultaneous Send requests give one job and one 409 while the page stays responsive (R21).

**Building the table (R4).** Per request: read today's list (module 02's `read_todo`-style date check, but non-fatal: a stale list yields the R5 banner); read each contact file through the module code, keeping `Person`, `Send days` and the valid-address flag; compute "due today" per channel with module 02's `parse_days`; read each module's `send_log.json` and take, for each person, today's newest **live** entry (`sent_at`, `delivery`, status) for the state column and for the resend eligibility of R17. Nothing is cached across requests. Privacy (R16): the contact files are read only through module code that keeps `Person`, `Send days` and a valid-address boolean — the address, number and contact name never enter a template, a response, a transcript or a CSV — every response gets `Cache-Control: no-store`, and the static files reference no external host.

**Preview (R6).** `build_message(person, items, today)` from module 02; the email subject and signature from module 04's defaults/overrides; shown as plain text. No side effects.

**Send (R7, R8, R17).** The page POSTs `{people_by_channel, mode, confirm_live, confirm_resend[]}`. The server validates, then queues one job. The job takes the scheduler lock if a WhatsApp step is present (R9), refusing inside the R10 window; runs the steps in order with `subprocess.Popen`, `-u`, stdout/stderr merged and scrubbed line by line into the job's output buffer (the polling endpoint reads it), a per-step wall-clock backstop matching each module's own ceiling plus a margin; then releases the lock, re-reads the logs (newest run row with `trigger: manual-ui`), and builds the outcome table (R12: the page polls `/api/job` roughly every second for state, step and scrubbed lines; the transcript goes to `outputs/05-manual-ui/jobs/` and files older than 30 days are deleted). A step that exits non-zero, times out or leaves no log row is shown failed with its scrubbed message and a link to its troubleshooting section; the UI never retries and never reports a send the module's log does not show (R19). Because the modules write the rows, every send is auditable from the Log page with `trigger: manual-ui` and `resend: true` where confirmed (R22).

**Rebuild (R11).** Same shape as the scheduler's Claude step: `Start-Process`-equivalent `subprocess.Popen` of `claude -p …` with the prompt on stdin, killed (`taskkill /T /F`) after 10 minutes; success = `todo_by_name.json` dated today.

**Log page (R13).** `merge_rows()` = ledger rows ∪ legacy rows from module 02's `send_log.json` with `date <` the ledger's first date; sorted newest first; filter in Python from query parameters; CSV via the same filtered list.

**Refresh email receipts (R14).** A job that runs `send_email.py --reconcile` (confirm: Outlook may start), then re-reads the ledger; the Log page carries one sentence explaining that WhatsApp receipts cannot be refreshed later.

**Lock helper (R9).** `acquire_scheduler_lock()` uses `os.open(path, O_CREAT|O_EXCL|O_WRONLY)` and writes `{pid, started}` with an ISO timestamp (the format the PowerShell wrapper parses); a held lock is "live" if its pid is alive (`OpenProcess`/`GetExitCodeProcess`, never `os.kill`, which would terminate a process on Windows) and it is younger than 30 minutes. Same function as module 04's.

**Launcher (R18).** `start_ui.cmd` tries `python`, then `py -3`, then the Python install under `%LOCALAPPDATA%`, runs `app.py`, and opens the browser to the tokened URL after the server answers. `make_shortcut.ps1` writes the `.lnk` to the Start Menu folder only.

## 10. Risks & Mitigations
| Risk | Impact | Mitigation |
|---|---|---|
| **Another website in the owner's browser triggers a send** (cross-site POST, DNS rebinding) | Real colleagues messaged without the owner's knowledge | Loopback only, `TRUSTED_HOSTS`, a per-start token in an `HttpOnly`/`SameSite=Strict` cookie, same-origin check on every POST, nothing on `GET` (R1, R2, R17); T2 |
| A manual job holds the scheduler's lock at 10:00 | The day's scheduled run logs `skipped_locked` and is **not** retried, so nobody gets the list | The ±window guard (R10) for WhatsApp/Rebuild jobs; email-only jobs avoid the lock; T11/T12 prove the failure mode really exists |
| The UI and a terminal run collide on WhatsApp | Two Chrome sessions corrupt `.secrets/wweb-auth` (it has happened) | The UI takes the scheduler's lock (R9). A terminal run of module 02 still bypasses it — an existing gap the UI narrows but cannot close; stated in §12 |
| A mis-click sends live | Real people get a message that should have been a test | `dry-run` default reset every load, an unmissable `live` colour, a confirm listing the exact people, a separate resend confirm, and server-side re-validation (R7, R17) |
| The page leaks a number, address or token | Private data on screen or in a log | Only `Person`/`Send days`/a boolean are read; scrubbed output; token never on disk; no external resources (R2, R16, R3); T25 |
| The legacy rows mislead (no `delivery`, no `trigger`) | The owner reads old `sent` as "delivered" | Marked `legacy`, `delivery` blank, trigger `unknown` unless the run has one (R13) |
| Rebuild spends money repeatedly | Recurring cost | A confirm stating the cost, one job at a time, the cost visible afterwards (R11, T23) |
| The Werkzeug debugger or reloader is on | Code execution from the browser | Never enabled (§7 "Server start"); T1/T18 check |
| The Python launcher resolves to the Microsoft Store alias | `start_ui.cmd` fails silently | The launcher tries `python`, `py -3`, then the real install path (R18, T19) |
| A shortcut on the synced Desktop | A path from this laptop syncs to the cloud | Start Menu only (R18, T19) |
| The UI hangs on a module that never returns | A stuck job and a held lock | Per-step backstops plus the modules' own ceilings, the 30-minute/dead-pid lock rule, no cancel needed (R9, R19) |

## 12. Troubleshooting & Rollback
| Symptom | Likely cause | Detect | Fix |
|---|---|---|---|
| The page says 401 / "start the UI from the launcher" | The server was restarted (new token) or the cookie is gone | the message | Use `start_ui.cmd` (it opens the tokened URL) |
| `start_ui.cmd` does nothing | `python` is the Microsoft Store alias, or Flask is missing | the console message | The launcher tries `py -3` and the real install; `python -m pip install flask` if Flask is missing |
| "The UI is already running" | A second start found a live server | the message names the port | Use the open window, or `start_ui.cmd --stop` |
| Send/Rebuild buttons are disabled with "a run is in progress" | The scheduler (or another job) holds `outputs/03-scheduler/run.lock` | the status strip shows who/since | Wait; a lock from a dead process or older than 30 minutes is reclaimed automatically |
| A job is refused "the scheduled run is about to start" | The 10:00 guard (R10): within 6 minutes before to 3 minutes after `SCHED_TIME` | the message | Wait a few minutes — holding the lock now would make the scheduled run skip the day |
| All send controls are disabled and a banner says the list is old | `todo_by_name.json` is not from today | the banner shows its date | Press **Rebuild list**, or wait for the 10:00 run |
| A person is unticked though the day matches | Already sent today, no items, or (email) no valid address | the state column | Resend needs the confirm; fix the contact row for an invalid address |
| A WhatsApp row shows `server` or `pending` | The recipient's phone had not confirmed within the wait | the Log's colour and `delivery` | Check the chat on the primary phone; resend only if it still shows one tick hours later |
| A manual WhatsApp send fails with "browser already running" | A terminal run of module 02 (not the UI) holds the Chrome profile | the job's scrubbed output | Close the other run; always use the UI or the scheduler for WhatsApp |
| The Log shows old rows with no delivery column | They are `legacy` rows from before 2026-10-19 | the `source` column | Expected: those sends predate delivery receipts |
| Email shows `queued` | Outlook was offline | the Log | It sends when Outlook reconnects; do not resend |
