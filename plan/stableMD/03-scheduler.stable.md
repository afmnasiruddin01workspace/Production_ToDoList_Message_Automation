## 2. Goal
Run the whole pipeline by itself at **10:00 Asia/Dhaka every day** on this Windows laptop, with no
window and no human present: launch headless Claude Code, have it run skill `01-calendar-todo` and
then `02-whatsapp-message`, verify from the artifacts that both actually did their job, and tell the
owner — by WhatsApp, a Windows toast, a log and a visible window — whenever a run fails or needs him.

**Why v2.0 (2026-10-19).** The owner asked for the same list to go out **by email** as well (module 04), automatically at 10:00 like WhatsApp, with proof of what was delivered. So the daily run now has **two channels, WhatsApp and email, that succeed or fail independently**: module 01 builds the list once; WhatsApp (module 02, via the headless Claude session as before) and email (module 04, run directly by the wrapper — it is deterministic and needs no Claude) each deliver it; a failure of one never stops the other from being attempted. Two further fixes ride along: (1) a **missed-run catch-up** (laptop asleep at 10:00, run starts on wake) was being mislabeled `manual-gui` by v1.1's time-window rule — found on 2026-10-02, when it would have lost its automatic retries; launches are now classified from what Task Scheduler itself logged about them; (2) every scheduled run is now labeled with its trigger in the module 02 / 04 logs, so the delivery ledger can tell a scheduled send from a manual one. Adding fields and statuses to the run log changes the §4 contract, so this is a **MAJOR** bump (v1.1 → v2.0) under `docs/UPGRADE.md`.

**Why.** Modules 01 and 02 are stable but only fire when the owner remembers to open Claude Code. A
forgotten session means colleagues silently get no to-do list that day. This module removes the owner
from the daily path and puts him back only when something is actually broken.

**Why headless Claude and not a plain script.** Module 01 is *agentic*: Claude itself performs its ten
steps, calling the claude.ai Google Calendar connector for events. Only a Claude session can reach that
connector, so the scheduler drives Claude rather than re-implementing module 01 in Python. The owner
chose this over porting module 01 to the Calendar API (2026-09-19).

## 5. Scope

**In scope**
- A Windows Task Scheduler task firing at 10:00 local time, all 7 days, hidden, as the logged-on user.
- Catch-up when the machine was off or asleep (start-when-available), and retry twice at 15-minute intervals — **a catch-up run is recognised as a scheduled run (R17) and keeps its retries (R18)**.
- **(v2.0)** The email channel: running module 04 directly after the Claude step, independently of WhatsApp (R19–R22), with its own pre-flight scope (R20), verification (R21), and a toast-only digest of delivery warnings (R23).
- **(v2.0)** Labelling each scheduled run's trigger in modules 02 and 04's own logs (R24).
- A single-instance lock so a scheduled run never collides with a manual one.
- A pre-flight health check that refuses to start the pipeline when a prerequisite is broken.
- Driving headless `claude -p` with a fixed prompt and an explicit, least-privilege permission set.
- A hard wall-clock timeout that kills a stuck run (notably an unattended Google re-consent prompt).
- Artifact-based verification that both modules really produced today's work.
- Four alert channels on failure: WhatsApp to the owner's own number, Windows toast, the run log, and a
  visible console window.
- `run_log.json` plus a per-run transcript, and a run summary.
- An idempotent installer/uninstaller for the scheduled task.

**Out of scope**
- Changing anything in modules 01, 02 or 04 — all are invoked exactly as published (module 02 through the Claude session, module 04 directly with its published options).
- Starting, signing in to, or repairing Outlook: module 04 owns that (it starts Outlook with an explicit profile when closed). A dialog Outlook raises on its own is module 04's risk, bounded by its own ceiling.
- Cloud or always-on scheduling. This is a laptop-only design; if the laptop is off all day, no run happens.
- Performing the Google sign-in or the WhatsApp QR scan automatically. Both are *detected and alerted*,
  never automated — they are deliberate human gates.
- Waking the machine from full shutdown, and any BIOS/power-plan changes.
- Delivery/read receipts of its own, and any change to message content or the send schedule. (The wrapper only *reports* what modules 02 and 04 record, R23.)
- Running module 02 directly instead of through Claude. It would be cheaper and would set the trigger label deterministically, but changing how a stable path runs is a separate decision; v2.0 keeps the Claude session and labels the trigger through the prompt (R24) with a check that warns if the label is missing.
- Committing, pushing or tagging anything from the scheduled run.

| R16 | **(v1.1, amended v2.0)** A launch whose `-Trigger` is `schedule` that R17 cannot classify from Task Scheduler's own events (the log is disabled, unreadable, or holds nothing about this launch) is reclassified as `manual-gui` if the wall-clock start time falls outside a window around `SCHED_TIME` (5 minutes before, through every configured retry interval plus slack after). | R17 | **(v2.0) Launch classification from Task Scheduler's own log.** For a `-Trigger schedule` launch that is not a continuation (R18), the wrapper reads `Microsoft-Windows-TaskScheduler/Operational` for events whose message names `\ToDo-WhatsApp-Daily` in the 2 minutes before the script started. The log is queried by event id and then filtered by task name (event 114 is raised hourly by other machine tasks, so the name is essential). **The most recent trigger event decides**: **107** ("due to a time trigger condition") → **`schedule`**; **114** ("could not launch … as scheduled … started now … if schedule is missed", e.g. the laptop was asleep at 10:00) → **`catch-up`**; **110** ("launched … for user", written for a user's "Run") → **`manual-gui`** **even inside the 10:00 window**. "Most recent" matters: a manual launch a few seconds after a real time-triggered one has both a 107 (the earlier launch) and its own 110 in the look-back, and testing for "any 107" misclassified it as `schedule` (found by the live test T23, 2026-10-19). If none of 107/114/110 is present but the launch's own events (100/129/200) are, it is `manual-gui`; if there are no events at all (log disabled, rolled over, unreadable) R16's window rule decides. The decisive event id is stored as `launch_event` (`none` when the window rule decided). A `catch-up` run is a scheduled run in every respect: it takes the lock, counts toward the attempt ladder, alerts only at the last attempt, and self-retries — it need not fall inside the 10:00 window. Classification happens once, at script start, because the log is a 10 MB circular log (≈6 days on this machine) and is useless for archaeology. |
| R18 | **(v2.0) Continuations keep their label.** The wrapper's self-retry (R11) re-invokes itself with `-Trigger schedule -ContinueFrom <label>`, where `<label>` is the label this attempt ended with (`schedule` or `catch-up`). A launch with `-ContinueFrom` takes that label as given, without consulting the log or the window (a retry fifteen minutes after a 16:21 catch-up is nowhere near 10:00, and no Task Scheduler event announces it). `-ContinueFrom` is only valid with `-Trigger schedule`, and only `schedule` or `catch-up` are accepted. Today's attempt number counts failed rows whose trigger is `schedule` **or** `catch-up`. |
| R19 | **(v2.0) The email step.** After the Claude step, and whether or not it succeeded, the wrapper runs module 04 **directly** — `python .claude/skills/04-email-message/send_email.py --trigger <schedule|manual>` with `EMAIL_MODE` forced per R4 — provided (a) `SCHED_EMAIL` is not `0`, (b) the email pre-flight scope passed (R20), and (c) `outputs/01-calendar-todo/todo_by_name.json` is dated today. It must run even when the Claude step failed, because module 02 can fail after module 01 has already produced today's list. Its stdout and stderr go to `outputs/03-scheduler/logs/<stamp>.email.txt` and `<stamp>.email.err.txt` (module 04 scrubs addresses and long numbers itself). The step is bounded by `SCHED_EMAIL_TIMEOUT_MIN` (default 10) of wall clock; on expiry the process tree is killed and the email channel is `failed` (module 04 has its own, shorter ceiling, so this is the backstop). The trigger passed to modules 02/04 is `schedule` for `schedule` and `catch-up`, and `manual` for `manual` and `manual-gui`. |
| R20 | **(v2.0) Channel independence.** A failure of either channel never prevents the other from being attempted, as long as today's list exists. By pre-flight scope: a **`shared`** failure (Google token, `lists`, `tools`, `disk`, `network`) → `preflight_failed`, nothing starts, both channels `skipped` (without a list there is nothing to send); a **`whatsapp`** failure (`contacts`, `wa_session`, `wa_config`, `wa_network`) → module 02 is **not** run this time (the per-run prompt tells Claude to run module 01 only and stop), the WhatsApp channel is `preflight_failed`, and **the email step still runs**; an **`email`** failure (`email_config`) → the email step is skipped, the email channel is `preflight_failed`, and **WhatsApp still runs**. Each channel's own failure (a `claude_failed`/`verify_failed`/`timeout` on the WhatsApp side, an `email_failed` on the other) likewise leaves the other channel's delivery in place. |
| R21 | **(v2.0) Email verification.** After the email step the wrapper reads `outputs/04-email-message/send_log.json` and requires a run for today with the run's mode; it aggregates every such run (a retry's row can legitimately show `sent: 0` because attempt 1 delivered) into `verify.email` = `{sent, failed, unconfirmed, skipped, invalid_address, accepted, queued, bounced}`. The email channel is `failed` if the process exited non-zero, if no run for today with the run's mode exists, if module 04 printed `skipped_locked` (another email run held its lock — `"module 04 was locked by another run"`, so the retry picks it up), or if the **newest** such run row has `failed` or `unconfirmed` greater than 0 (judging the newest row, not the sum: a person left `unconfirmed` by attempt 1 is `already_sent` on attempt 2 and must not fail every later retry — the earlier `unconfirmed` surfaces as a warning, R23); `ok_nothing_to_send` if `sent` is 0 across today's rows and nothing failed; otherwise `ok`. `queued`, `bounced` and `invalid_address` do **not** fail the channel (the mail was handed over, or the contact file needs the owner) — they are warnings (R23). |
| R22 | **(v2.0) Overall status and its precedence.** The run's `status` is the first that applies: `skipped_locked` → `preflight_failed` (shared) → `timeout` → `claude_failed` → `verify_failed` → `whatsapp_preflight_failed` → `email_preflight_failed` → `email_failed` → `ok_nothing_to_send` (both channels `ok_nothing_to_send` or skipped by design) → `ok`. Whatever the precedence picks, `channels.whatsapp` and `channels.email` each record their own outcome, so a `claude_failed` run still shows whether email delivered. Every status other than `ok`, `ok_nothing_to_send` and `skipped_locked` is a failure for the attempt ladder, the retry and the alert (R10, R11). |
| R23 | **(v2.0) Delivery warnings, toast only.** After the channels have run, the wrapper adds to the run row's `warnings` one short string for each of: WhatsApp `summary.not_delivered` > 0 ("N WhatsApp message(s) not confirmed delivered"), WhatsApp or email `unconfirmed` > 0 on any of today's rows ("N … unconfirmed — check the chat / Sent Items"), email `bounced` > 0, `queued` > 0, `invalid_address` > 0, and a missing trigger label (R24). If there are any **and the run's status is `ok` or `ok_nothing_to_send`**, it fires **one Windows toast** summarising them and nothing else — never the WhatsApp message, the window or an attempt retry, and the run's status is unchanged (on a failing run the warnings are in the row and the failure alert already speaks). Counts are summed over every module 02 / module 04 run row for today in the run's mode. No name, address or number appears in a warning. |
| R24 | **(v2.0) Trigger propagation.** The wrapper writes a per-run copy of `prompt.txt` into `outputs/03-scheduler/logs/` with the `{TRIGGER}` placeholder replaced by `schedule` or `manual` (R19's mapping) and feeds that copy to Claude; the prompt tells Claude to append `--trigger {TRIGGER}` to the `send_whatsapp.py` command module 02 runs. The email step passes the same flag itself. After the run, if the newest `live`/mode-matching module 02 row for today has a different or missing `trigger`, the wrapper records the warning "whatsapp trigger label missing" (R23) — a label, not a delivery, so never a failure. |
| R25 | **(v2.0) Files, settings and hygiene.** `scheduler.env` gains `SCHED_EMAIL` (default `1`), `SCHED_EMAIL_TIMEOUT_MIN` (default `10`) and `SCHED_RETRY_WAIT_SEC` (default `900`; a test hook as much as a setting). Every `SCHED_*` setting may also be given as an environment variable, which overrides `scheduler.env` (so tests need not edit the owner's file). Test-only hooks, documented in the script: `-ClassifyOnly` (prints the R17 classification and exits), `SCHED_LAUNCH_TASK` / `SCHED_LAUNCH_REF` / `SCHED_LAUNCH_LOG` (aim the classifier at another task, time or log), `SCHED_PREFLIGHT_SKIP` (comma-separated pre-flight ids to skip), `SCHED_CLAUDE_EXE`. The email transcript is pruned with the others after `SCHED_RETENTION_DAYS`. `scheduler.env.sample` (and the owner's real `scheduler.env`) no longer say that Task Scheduler supplies the retries — they live in the wrapper (R11) — and `SCHED_MAX_ATTEMPTS` is described accordingly. When the wrapper has to kill the Claude step or the email step (R6, R19), it also deletes any job/result temp files modules 02 and 04 created during that step, because the killed process never reaches its own cleanup and those files hold real numbers or addresses. Module 03 never reads an address, a `Number` or a `WhatsApp contact name`; nothing it writes (run log, transcripts, toasts, the visible window) contains an address or an 8+ digit run. |
| R26 | **(v2.0) A running Outlook is not required, and not touched by pre-flight.** Because module 04 starts Outlook itself with an explicit profile when it is closed (module 04 R12), the scheduler neither requires Outlook to be open at 10:00 nor starts it. ## 7. Steps / Design

Four files under `src/scheduler/`, plus the skill. **v2.0 changes `run_daily.ps1`, `preflight.py`, `prompt.txt` and `scheduler.env.sample`; nothing in modules 01, 02 or 04 is modified.**

```
Task Scheduler "ToDo-WhatsApp-Daily"  (10:00 daily · hidden · start-when-available · 2 retries × 15 min)
  └─ conhost.exe --headless pwsh -NoProfile -File src/scheduler/run_daily.ps1   (no window at all; -WindowStyle Hidden is ignored on Win11)
       1. lock        outputs/03-scheduler/run.lock          (R2, R15 - atomic acquire)
       2. preflight   python src/scheduler/preflight.py      (R3)
       2b. classify    Task Scheduler events 107 / 114 / launch  (R17, R18)
       3. pipeline    WA_MODE=live claude -p … --settings …  (R4, R5, R6, R7, R20: module 01, then 02 unless its pre-flight scope failed)
       3b. email      EMAIL_MODE=live send_email.py          (R19: runs whenever today's list exists)
       4. verify      artifacts, not exit codes, per channel (R8, R9, R21, R22)
       4b. warnings   delivery digest, toast only            (R23)
       5. log         outputs/03-scheduler/run_log.json      (R12)
       6. alert       log · toast · WhatsApp · window        (R10, R11)
       7. unlock      always                                 (R2)
```

**`run_daily.ps1`** — the wrapper; the only thing Task Scheduler knows about.
1. Resolve the repo root from `$PSScriptRoot`, load `src/scheduler/scheduler.env` (including the v2.0
   keys `SCHED_EMAIL`, `SCHED_EMAIL_TIMEOUT_MIN`, `SCHED_RETRY_WAIT_SEC`, R25), parse the
   `-Trigger`/`-Mode`/`-Visible`/`-ContinueFrom` parameters (R13, R18). Every path is derived from `$PSScriptRoot`, never
   from the current directory, so the script behaves identically whether Task Scheduler launches it or
   the owner runs it by hand from any folder — this is what makes the whole test ladder below possible
   without touching the registered task.
2. Determine the effective trigger. With `-ContinueFrom` (R18) it is that label. Otherwise a
   `-Trigger schedule` launch asks `Get-LaunchReason` (R17): it queries the Operational log with
   `Get-WinEvent -FilterHashtable @{LogName=…; Id=107,114,110,100,129,200; StartTime=<start − 2 min>}`,
   keeps events whose message contains `\ToDo-WhatsApp-Daily`, and lets the **most recent** of 107 → `schedule`,
   114 → `catch-up`, 110 → `manual-gui` decide (launch-events-only → `manual-gui`, nothing → R16's window rule;
   `launch_event` records which). The
   function takes the task name and a reference time as parameters so the test ladder can aim it at other
   tasks' real events. Take the lock via an atomic create (R2, R15) — no check-then-write gap. Held and live → log
   `skipped_locked`, alert (toast only), release nothing, exit 0.
3. Run `preflight.py`, capture its JSON, group failures by `scope` (R20). A `shared` failure →
   `preflight_failed`, alert with the failed check's `fix` text, exit 1 (so the self-retry applies). A
   `whatsapp` failure → remember to skip module 02; an `email` failure → remember to skip the email step;
   both still let the run continue.
4. Run `claude` (R5) as a child process with `WA_MODE` forced (R4), `--output-format json`, a job object
   for the timeout (R6), stdout/stderr tee'd to `outputs/03-scheduler/logs/<stamp>.json`. The prompt it
   reads is the per-run copy of R24: `{TRIGGER}` filled in, and — when the WhatsApp scope failed — the
   module 02 step replaced by "Do not run module 02 this time; stop after module 01 and print
   `SCHEDULER_OK module 01 only`". A Claude failure no longer ends the run: it is recorded as the
   WhatsApp channel's result and the wrapper goes on to step 4b **if today's list exists**.
4b. Run the email step (R19): `python send_email.py --trigger …` with `EMAIL_MODE` forced, output to
   `logs/<stamp>.email.txt`, killed at `SCHED_EMAIL_TIMEOUT_MIN`. Neither pre-flight nor this step starts or
   requires Outlook (R26): module 04 starts it with an explicit profile when it is closed, and a minimised
   window then stays open.
5. Verify the artifacts per channel (R8, R21), compute `channels`, classify the status by R22's
   precedence (R9), and build the `warnings` digest (R23, R24), firing its single toast.
6. Append the run entry to `run_log.json`, prune to 60 days (R12).
7. Alert immediately if the effective trigger is `manual-gui`, or if this is a `schedule` failure at
   the final attempt (R10, R11, R16); otherwise log only and let the self-retry (below) run.
8. `finally`: release the lock; exit 0 on success, non-zero on failure so retries fire.

**Retries live inside `run_daily.ps1` itself** (R11), not in Task Scheduler: `conhost --headless`
does not propagate the child's exit code, so Task Scheduler's own `RestartCount` can never see a
failure to restart (found 2026-09-21). A `schedule`-effective failure below `SCHED_MAX_ATTEMPTS`
waits `SCHED_RETRY_WAIT_SEC` (15 minutes) and re-invokes itself with `-Trigger schedule -ContinueFrom <label>` (R18), so a retry of a catch-up run stays a `catch-up` run; a `manual-gui`-effective failure
(R16) never does this, so a stray click at the wrong time of day cannot chain into a retry loop
that is still running when the real fire arrives (found 2026-09-23).

**`preflight.py`** — Python 3, stdlib plus the `google-auth` libraries module 01 already depends on.
Each check returns `{id, scope, status, detail, fix}` with `detail` free of secrets (v2.0 adds `scope`, R3). The Google check loads
`token.json` directly and calls `creds.refresh(Request())` **only when a refresh token is present**;
it never constructs an `InstalledAppFlow`, so it can report `needs_signin` instead of hanging (R3a).
The WhatsApp check shells out to `send_whatsapp.py --check` and reads its output. **The email check (v2.0) shells out to `send_email.py --check` with `EMAIL_MODE=live` in its environment, and imports `win32com` in a child Python; it reads only the masked lines `--check` prints ("classic Outlook: found", "outlook profile: set (name withheld)", "contacts: N people, M with a valid address") and never starts Outlook.**

**`notify.py`** — one entry point, `notify(title, body, channels)`.
- *toast*: WinRT from PowerShell (`Windows.UI.Notifications.ToastNotificationManager`) under the built-in
  PowerShell AppId — `BurntToast` is not installed and is not made a dependency.
- *whatsapp*: builds a one-recipient `wa_send.js` job (`{mode:"live", sender, auth_dir, chrome,
  min_delay:0, max_delay:0, qr_timeout:15, recipients:[{person:"scheduler", to:<WA_TEST_NUMBER>,
  parts:[body]}]}`) in the system temp dir, runs the worker with a 90 s bound, deletes both files.
- *window*: `Start-Process pwsh -WindowStyle Normal` showing the failure, the failed check and its fix,
  held open until dismissed.

**`install_task.ps1`** — `Register-ScheduledTask` with `-Settings (New-ScheduledTaskSettingsSet
-StartWhenAvailable -RestartCount 2 -RestartInterval (New-TimeSpan -Minutes 15)
-MultipleInstances IgnoreNew)`, `-Trigger (New-ScheduledTaskTaskTrigger -Daily -At 10:00)`,
`-User nasir9781 -RunLevel Limited`, action = hidden `pwsh -File run_daily.ps1`. Re-running updates in
place (R1). `-Uninstall` unregisters (R14). The machine's timezone is already +06:00, so 10:00 local
**is** 10:00 Asia/Dhaka — no conversion anywhere.

**`scheduler.settings.json`** — a deny-list, not an allow-list (R7). Testing (T10, T15, 2026-09-19)
showed `allow` requires *every* component of a compound Bash command to be individually allowed, while
module 01 is agentic and issues compound commands (`cd … && mkdir … && python … ; rm …`) whose exact
shape varies run to run — narrowing `Bash` in `allow` stopped the pipeline dead twice. `deny`, by
contrast, fires if *any* component matches (verified directly), so it is a real boundary even for Bash.
The permission set is therefore: bare `Skill`/`Read`/`Write`/`Edit`/`Bash` in `allow`, with `deny`
carrying `Bash(git:*)` (blocks any shell command containing git, protecting the repo and its secrets
from an off-script run) plus path-scoped `Read`/`Write`/`Edit` denies over `.secrets/`, `src/`,
`.claude/`, `plan/`, `docs/`, and the top-level project files. `Bash(rm:*)` is deliberately **not**
denied — it blocked module 01's own cleanup of its temp file inside `outputs/` (T15), and `deny` cannot
carry a path exception. Real containment rests on `deny Bash(git:*)`, the path-scoped file denies,
`prompt.txt`'s own rules, and the task launching nothing beyond the two published skills. See the
`_comment` block in `src/scheduler/scheduler.settings.json` for the full measured behaviour. If module 01
is ever made non-agentic (parsing moved into a script with a fixed command shape), narrow `Bash` back.

**The fixed prompt (R5)** — stored in `src/scheduler/prompt.txt` so it is reviewable and diffable:

> Run the daily pipeline non-interactively. Never ask a question; if anything blocks you, stop and print
> `SCHEDULER_FAIL: <reason>`.
> 1. Invoke the Skill tool with skill `01-calendar-todo` and follow it exactly.
> 2. Only if step 1 wrote `outputs/01-calendar-todo/todo_by_name.json` with today's date, invoke the
>    Skill tool with skill `02-whatsapp-message` and follow it exactly, **adding `--trigger {TRIGGER}` to the
>    `send_whatsapp.py` command** (R24). *(When module 02's pre-flight scope failed this line is replaced by
>    "do not run module 02; stop after module 01", R20.)*
> 3. Print `SCHEDULER_OK` followed by each module's run summary.
> Do not write outside `outputs/`. Do not run git. Do not print any phone number, token or `.secrets` value.

**Promoting to stable v1.0** on the strength of: 3 real unattended 10:00 runs (2 failed-and-recovered, 1 clean), the retry loop proven live, the window bug fixed and re-confirmed, and 17/18 tests passing with the 18th an accepted, non-blocking gap.

**Open design gaps (each needs its own draft, not an in-place edit):** (1) module 02 v1.2 — write an intent record before sending, since `send_log.json` is written only at the end and a hard kill can leave a sent-but-unlogged message that a retry would repeat; (2) an unfinished-run marker in `run_daily.ps1`, so a hard kill (no `finally`) is reported by the next run instead of passing silently.

The scheduled task **is installed** (`ToDo-WhatsApp-Daily`, daily 10:00, hidden, next run 2026-09-20 10:00) and has been fired successfully by hand.

Nine real defects were found and fixed during this phase — see §12 for each: duplicate `run_log` rows from `exit` inside `try`; a benign `skipped_locked` escalating to WhatsApp and a popup; `Start-Process` not quoting the space in the repo path; the pre-flight reporting a traceback header instead of the error; `permissions.allow` not restricting anything without `--permission-mode manual --permission-prompts none`; `Write(outputs/**)` in `allow` matching nothing and denying the whole pipeline; `alerts_failed` missing from the run log so a failed alert channel vanished; the scheduled task pointing at a **version-stamped** PowerShell path that would break on the next update; and `Bash(rm:*)` in `deny` blocking module 01's own temp-file cleanup. A tenth was found in **module 02** and fixed there as v1.1 (`send_log.json` overwrite — incident filed).

Two findings worth carrying forward rather than filing away:
1. **`deny` is a real boundary for Bash, `allow` is not.** `deny` matches any component of a compound command; `allow` requires every component to match. This asymmetry decides the whole permission design (R7).
2. **Module 01's agentic execution is non-deterministic in shape.** The same pipeline passed at 12:25 and failed at 12:47 with no configuration change, purely because the agent composed a different shell command. Any tightening of `deny` will therefore break intermittently rather than consistently.

## 10. Risks & Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| **Unattended Google re-consent hangs the run forever** — `fetch_tasks.py` falls back to `run_local_server()` with nobody there to click | The task sits stuck, the lock is held, no messages go out, and nothing tells the owner | R3a tests the refresh without ever reaching `InstalledAppFlow`, so the run is refused *before* it starts; R6's hard timeout kills anything that still stalls; R2 always releases the lock |
| OAuth consent screen is External+Testing, so the refresh token dies every 7 days | The automation breaks weekly | Pre-flight names it as `needs_signin` with the exact fix; the owner is deciding whether to publish the app to In production. Documented in §12 either way |
| WhatsApp session drops and wants a QR scan | Nothing sends; the worker waits 120 s then exits | Pre-flight (d)(e) catches the missing/empty session before the pipeline starts and alerts with "scan from Settings → Linked devices" |
| Two runs open `.secrets/wweb-auth/` at once and corrupt the session | The session has to be deleted and re-linked (this already happened once) | R2's lock, plus `-MultipleInstances IgnoreNew` on the task itself |
| Headless Claude deviates from the skill and produces a wrong or partial grouping | People get a wrong list, silently | R8 verifies artifacts rather than exit codes; the transcript is kept for every run; the prompt is fixed in `prompt.txt` and diffable; the permission set stops it doing anything outside `outputs/` |
| A broad permission set lets an unattended agent do damage | Arbitrary writes or a stray git operation | R7's explicit allow/deny instead of `--dangerously-skip-permissions`; unlisted tools are auto-denied in headless |
| Daily token cost grows unnoticed | Recurring spend | `total_cost_usd` is recorded per run in `run_log.json`; T18 records the real per-run figure; `SCHED_MODEL` defaults to the cheaper Sonnet |
| The laptop is off all day | Nobody gets their list and the owner may not notice | Start-when-available catches the same day on wake; if the whole day is missed, the next day's run still sends a current list. Accepted limitation of a laptop-only design |
| An automated alert leaks a phone number into a toast or a log | Private data on screen or in a file | R12 + T17: everything masked to 4 digits, `outputs/**` and `.secrets/**` git-ignored |
| The scheduled run sends in `live` while the owner is mid-test | Real colleagues get a test-era message | R4 forces `live` only for the scheduler's own run; the manual wrapper takes `-Mode`; module 02's cap and `already_sent` bound the blast radius; `install_task.ps1 -Uninstall` switches the whole thing off in one command |

| **(v2.0)** A missed-run catch-up is mislabeled `manual-gui` and loses its retries | A day with a failed first attempt is never retried and alerts at once | R17 classifies from Task Scheduler's own event 114, R18 keeps the label across retries; T23/T25 |
| **(v2.0)** The Task Scheduler Operational log is a 10 MB circular log (≈6 days here) or has been disabled | Classification has no evidence to use | It is read at launch time only, never later; with no events R16's window rule is the fallback and `launch_event: none` makes that visible; T24 |
| **(v2.0)** The first real email run happens unattended | An Outlook problem is discovered at 10:00 rather than in a test | Module 04's ceiling, `/profile` start and idempotency; the email channel is independent so WhatsApp is unaffected; T39 is run only with the owner's approval and the next-morning log review |
| **(v2.0)** Outlook is closed at 10:00 and module 04 starts it | A minimised Outlook window appears and stays open | Documented (R26, §12); not an alert |
| **(v2.0)** The wrapper takes noticeably longer (module 04 waits ~30 s for bounces) | Later finish | Bounded by `SCHED_EMAIL_TIMEOUT_MIN`; the email step runs after the Claude step so WhatsApp is never delayed by it |
| **(v2.0)** WhatsApp pre-flight failure no longer stops the whole run | A broken WhatsApp session could go unnoticed because email "succeeds" | It is a failure for the attempt ladder and alerts at the last attempt (R22), with `channels.whatsapp: preflight_failed` visible |
| **(v2.0)** The prompt-based trigger label is ignored by Claude | Module 02's rows say `manual` for a scheduled run | R24 checks the row and records a warning; the label is cosmetic and never gates delivery |
