| 2026-09-22 | 02-whatsapp-message | 1.2 | Worker deadlines (R18–R22): the WhatsApp worker must reach `ready` within `WA_READY_TIMEOUT` (120s) or it gives up with nothing sent (`startup-timeout`); each recipient's send is bounded by `WA_SEND_TIMEOUT` (60s), and a timeout marks that person `unconfirmed` (never auto-resent, since a retry could otherwise double-message them) rather than `failed`; Python enforces a hard ceiling and kills the whole worker/Chrome tree if it's exceeded; the worker rewrites its result file after every recipient so a kill never loses the record of who was already reached; timestamped stage lines (`launching → loading → authenticated → ready → sending`) name where a hang stalled. New status `unconfirmed`. Built after module 03's real 10:00 runs hung ~10 minutes unbounded on 2026-09-20/21; confirmed live in production on 2026-09-22 — the `startup-timeout` fired correctly and the scheduler's retry recovered automatically with no messages lost or duplicated. |
| 2026-09-22 | 03-scheduler | 1.0 | First stable release. Windows Task Scheduler fires a hidden pipeline daily at 10:00 Asia/Dhaka: pre-flight checks, then a headless `claude -p` session running skills `01-calendar-todo` then `02-whatsapp-message`, verified from the artifacts (not exit codes), with a lock against overlapping runs and alerting (WhatsApp, toast, log, visible window) only once retries are exhausted. Launches via `conhost.exe --headless`, not `-WindowStyle Hidden`, because the latter is ignored on Windows 11 and a visible window killed the very first real run (`0xC000013A`); retries run inside the wrapper itself rather than via Task Scheduler's `RestartCount`, because the headless launcher doesn't propagate the child's exit code. Both fixes proven together on a fully unattended real run on 2026-09-22, which recovered automatically from module 02's worker-startup hang and delivered both scheduled messages. Known limitation: the root cause of that ~10:01 worker hang is still undiagnosed, though now bounded and recovered from automatically; missed-run catch-up (`StartWhenAvailable`) is configured but not yet observed live. |
| 2026-09-19 | 02-whatsapp-message | 1.1 | Hotfix: `send_log.json` no longer collapses each date to a single run. The retention filter used to drop earlier runs from today, so a same-day `dry-run` or `self` test destroyed that day's `live` row — losing the delivery audit trail and, because the idempotency guard counts only `live` rows, re-arming a double-send. Found during module 03 testing against real data. A date may now hold several runs, so consumers must select by `date` **and** `mode`. Regression tests T18/T19; incident `docs/incidents/2026-09-19-02-whatsapp-message-sendlog-overwrite.md`. |
| 2026-09-18 | 02-whatsapp-message | 1.0 | First stable release. Sends each person in `WhatsappContacts.txt` (new `Send days` column) their module 01 to-do list on WhatsApp via a **linked-device WhatsApp Web session** (`whatsapp-web.js`), not the Meta Cloud API — the owner's Facebook account is restricted, so no developer token can ever be issued. No token in this design; session lives in gitignored `.secrets/wweb-auth/` after a one-time QR scan. Test ladder: `dry-run` → `self` → `live`, capped and paced (`WA_MAX_PER_RUN`, randomized delay) since this is not an officially-supported channel. Known limitation: `sendMessage()` can succeed without returning a usable id (logged as `"unconfirmed"`, not a failure). |
