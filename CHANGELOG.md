| 2026-10-19 | 03-scheduler | 2.0 | **Email channel, independent channels, trigger classification — MAJOR** (the run log gains `launch_event`, `channels`, `warnings`, `verify.email` and three statuses). The daily run now has two channels that succeed or fail independently: WhatsApp (modules 01 then 02 through the headless Claude session, as before) and **email (module 04, run directly by the wrapper — deterministic, no Claude)**, each verified from its own log, so a failure of either never stops the other (a WhatsApp pre-flight failure skips module 02 but still builds the list and sends email; a failed Claude step after module 01 still lets email go; an email failure never touches WhatsApp). Pre-flight checks carry a `scope` and `network` is split. **Launches are now classified from Task Scheduler's own log** — event 107 time trigger → `schedule`, 114 missed-schedule → `catch-up`, 110 user "Run" → `manual-gui`, the most recent deciding — with the old clock rule as a fallback; a catch-up run keeps its automatic retries (the laptop-asleep run of 2026-10-02 had been mislabeled `manual-gui` and would have lost them) and retries carry their label through `-ContinueFrom` because a self-retry leaves no event. Delivery warnings (not-confirmed WhatsApp messages; bounced, queued, unconfirmed or invalid-address emails) raise one quiet toast and never a retry; the trigger label is propagated to modules 02 and 04 so the shared delivery ledger can tell a scheduled send from a manual one. Four defects found by testing and fixed, among them: a manual launch seconds after a real one was misclassified (found with a temporary real Task Scheduler task), and a killed step left its job file — real addresses/numbers — in the temp folder (the wrapper now cleans up; eight month-old module 02 job files from the hung runs of September were found and deleted). Tested in an isolated scratch copy of the repo plus real-system checks (real events, real pre-flight with Outlook closed, a real end-to-end dry-run with real Claude, $0.29). **Safety gate:** the owner's `scheduler.env` keeps `SCHED_EMAIL=0` until the first real emails are approved. **Untested at release, by owner decision:** the first real unattended run with the email channel (T39), scheduled for Wednesday 2026-10-21 and to be watched; no real colleague has yet been emailed by the scheduler. |

| 2026-10-19 | 04-email-message | 1.0 | First stable release. Emails each person in `EmailContacts.txt` the same to-do list module 02 sends on WhatsApp (module 02's text is imported, not copied), in the layout of the owner's reference screenshot (fixed subject, greeting, numbered list, signature, Aptos 12 pt HTML), on that file's own `Send days`, through the owner's classic Outlook via COM — no password anywhere. | 2026-10-19 | 02-whatsapp-message | 2.0 | Delivery receipts, manual options and a shared ledger (R23–R26) — MAJOR, because `send_log.json` gains fields. `sent` had only ever meant "the library did not throw": with `whatsapp-web.js` 1.34.7 (the latest stable) `sendMessage()` returns nothing, so all 35 live sends since 2026-09-24 were logged `message_id: unconfirmed`, and when the owner's desktop app showed "Waiting for this message" on that morning's 10:03 message the log could not say whether it had arrived. Each `sent`/`unconfirmed` entry now carries `delivery` (`read` · `delivered` · `server` · `pending` · `error`), taken from WhatsApp's own `message_ack` receipts while the worker is still connected and matched by exact message text; the run waits up to `WA_ACK_TIMEOUT` (45 s) for them and summarises `delivered` / `not_delivered`. Status and idempotency are unchanged, so someone at `server`/`pending` is never re-sent automatically. New CLI options for the manual-send UI — `--people`, `--resend` (logged `resend: true`), `--trigger` — and every outcome is appended to `outputs/delivery/delivery_log.json`, shared with the upcoming email module. Verified against the real WhatsApp session (T26–T33): online recipient reaches `delivered` in 3–6 s; a recipient with no internet stays at `server` and is reported "not confirmed delivered". Known limit: `delivered` is WhatsApp's report that the message reached the recipient's device, not proof the person saw it, and read receipts that arrive after the run ends cannot be captured. |
